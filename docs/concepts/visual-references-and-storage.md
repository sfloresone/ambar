# Visual references and synchronized storage

Status: conceptual prototype; implementation has not been authorized by this document.

Date: October 6, 2026.

## Product intent

Ámbar keeps content worth remembering or sharing immediately: photos, short clips, links and potentially other semi-static content, such as text or documents. A saved element should remain recognizable and available across devices, with sharing controlled by its owner.

For links, the current direction is to preserve the URL, useful metadata and a meaningful visual reference. Full website archiving is outside the current concept. It can be revisited separately if a concrete user need emerges.

Technical complexity should inform the implementation and its availability, while preserving useful choices for the user. Rich cards, screenshots and embedded views can coexist as representations of the same saved element.

## Agreed direction

- Offer an enriched card, a saved screenshot and an embedded view when available.
- Choose a suitable initial representation automatically and let the user change it.
- Preserve the user's presentation preference across devices.
- Keep the original link accessible regardless of the selected presentation.
- Preserve a visual reference that helps the user recognize what they saved.
- Distinguish the saved visual reference from live content, which may change.
- Load expensive or interactive representations when requested rather than loading every representation at once.

The initial-selection rules and the scope of each preference remain open product decisions.

## Representations

| Representation | What it shows | Useful for | Limitations |
| --- | --- | --- | --- |
| Enriched card | Title, description, domain and a representative image | Articles, products, videos and quick browsing | Metadata can be missing, generic or unrelated to what interested the user |
| Saved screenshot | An image of the page at a recorded time | Portfolios, design references, tools and visual layouts | Capture can show a cookie notice, login screen or blocked page |
| Embedded view | Live content within Ámbar, through an iframe or a provider's supported embed | Reading, playback and interaction without leaving the app | Availability depends on the source, browser and device; the content can change |

These representations belong to one element with one identity, ownership and sharing policy. Switching presentation should not create another saved element.

Open Graph metadata is a useful source for card titles, descriptions and images. Its image is a representative asset, not necessarily a screenshot or the page's main visible content. See the [Open Graph specification](https://ogp.me/).

### Embedding and capture are independent

A website can block framing through `X-Frame-Options` or CSP `frame-ancestors`. This does not, by itself, prevent a screenshot generated by opening the URL directly in an automated browser.

Conversely, allowing an iframe does not give Ámbar permission to read or capture another origin's document through ordinary browser JavaScript. A server-side capture worker or a platform-specific capability would be a separate mechanism.

See [frame restrictions](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Content-Security-Policy/frame-ancestors), the [same-origin policy](https://developer.mozilla.org/en-US/docs/Web/Security/Defenses/Same-origin_policy) and [Playwright screenshots](https://playwright.dev/docs/screenshots).

### Suggested presentation behavior

Show a lightweight saved reference while browsing the library. Activate the embedded content when the user opens or requests it. Offer the available representations without requiring the user to understand their technical implementation.

When an embed is unavailable, keep the screenshot or card usable and retain the action to open the original page. When automated preview generation fails, retain the saved link and allow a retry or a user-provided reference image.

Keep the timestamp of the saved reference visible where it helps distinguish it from the current page. Whether refresh replaces that reference or creates another version remains undecided.

## Proposed storage responsibilities

| Layer | Responsibility |
| --- | --- |
| Browser memory | Immediate interaction and temporary state if persistent storage is unavailable |
| IndexedDB | Local records, metadata, cached visual references, drafts and pending synchronization operations |
| localStorage | Small interface preferences; existing mock-session data only |
| Cookies | Real web authentication through HttpOnly, Secure session cookies |
| Backend database | Persisted records, ownership, sharing permissions, versions and synchronized preferences |
| Object storage | Uploaded media, documents, screenshots and copied preview images |

Save copies of visual assets used as persistent references, rather than relying exclusively on remote image URLs that can disappear or change. Cache the assets needed locally; a policy for cache size and eviction still needs definition.

IndexedDB is suitable for asynchronous access to structured records and blobs. Browser storage has quotas, can be unavailable or cleared, and is scoped to an origin and browser profile. Requesting persistent storage can help but does not replace remote preservation or automatically synchronize devices. See [IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API) and [storage quotas and eviction](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria).

Different landing and app origins do not share IndexedDB. Cross-origin handoff needs an explicit mechanism. Real authentication tokens must follow the repository's platform-specific rules and never be stored in IndexedDB or localStorage.

## Proposed save and share flow

1. Save the pasted URL locally and show the element immediately. Keep the local state distinct from remote confirmation.
2. Send the small record and chosen sharing permissions to the backend. Confirm remote persistence before presenting an Ámbar share link as ready for others.
3. Obtain metadata and generate or copy visual assets in the background. Update the existing element as each representation becomes available.
4. Synchronize records, preferences and asset references to other devices, updating their local copies.

Preview generation should not block saving a link or sharing a remotely persisted record. Offline saves remain pending until synchronized. The user can still share the original external URL independently of Ámbar's persistence.

An initial synchronization approach could use a durable queue, idempotent retries and record versions to detect conflicts. Creation, updates and deletions need explicit rules so retries do not create duplicates or restore deleted elements. A collaborative editing engine has not been selected; the current concept does not require simultaneous editing of a shared canvas.

## Performance and portability

Metadata extraction and automated capture belong in background backend work. Browser CORS rules prevent reading arbitrary websites directly unless the destination permits it. See [CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS).

Server-side capture keeps browser automation out of the client bundle but introduces processing cost and latency. Reuse existing references and use optimized image sizes for library browsing. Load embedded content on demand to control its network, memory and execution cost.

Domain types, validation and synchronization contracts belong in `@ambar/core` without browser or framework APIs. Browser persistence belongs in a guarded browser adapter. Platform-specific capture, authentication and storage capabilities come through the application boundary; native apps can reuse the domain contracts with different adapters.

External embed and capture integrations must respect the source's restrictions. Backend URL fetching needs URL validation, protection against private-network access, and bounded redirects, response sizes and execution time. Embed permissions and isolation require a separate implementation decision.

## Repository baseline

At the time of this note:

- [`packages/core/src/moment.ts`](../../packages/core/src/moment.ts) models `photo`, `clip` and `link`. A link currently includes its URL and optional title; it does not yet model these representations.
- [`packages/ui/src/lib/pending-moment.ts`](../../packages/ui/src/lib/pending-moment.ts) uses IndexedDB to recover one pending file during sign-in. It is not a synchronized library or a general operation queue.
- [`packages/ui/src/lib/clients.ts`](../../packages/ui/src/lib/clients.ts) provides mock authentication and uploads. Real backend clients and synchronization are not implemented yet.

This document does not change those contracts, add supported content types or select dependencies and backend providers.

## Research references

### Excalidraw

Excalidraw separates its scene and interface state in localStorage from files and its library in IndexedDB, using `idb-keyval`. Its local persistence includes grouped writes and handling of storage failures. See [LocalData.ts](https://github.com/excalidraw/excalidraw/blob/master/excalidraw-app/data/LocalData.ts).

For share links, it compresses and encrypts the scene, saves it remotely and uploads files separately. The link carries an identifier and decryption key in its fragment; it does not contain the entire scene. See [data/index.ts](https://github.com/excalidraw/excalidraw/blob/master/excalidraw-app/data/index.ts).

The useful inspiration is the separation between records, assets and local persistence. A shareable scene does not by itself provide Ámbar's account-based library synchronization. End-to-end encryption is a separate product decision because it affects server-side metadata processing, search and readings.

### Auorum

[Auorum](https://www.auorum.com/) is a visual product reference for recognizable saved links. The "Designed to use every day" section uses a prerecorded MP4 demonstration. Inspection of the landing page confirms the video, but does not establish whether the application's representations use metadata images, screenshots or iframes. Its internal implementation should not be inferred from the demonstration alone.

## Open decisions

- How should Ámbar choose the initial representation for each content type?
- Is presentation preference attached to the saved element, its owner, or each viewer? What does a share recipient initially see?
- Are captures automatic, requested by the user, or both? What crop or viewport best preserves the relevant content?
- Should refreshing a reference replace it or preserve a history?
- Which sources offer supported embeds, and how should availability be checked without relying solely on an iframe's load event?
- What is the experience for authenticated pages and platform-specific captures?
- How much content should remain available offline, and how should local cache limits behave?
- How should simultaneous changes across devices be reconciled?
- Which capture service or worker, metadata extractor and backend should be selected after validating the experience?

The next step is to validate the experience with representative links across devices before turning this concept into an implementation specification.
